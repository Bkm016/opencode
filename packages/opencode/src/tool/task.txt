Delegate bounded work to specialized child agents. Default: async; returns task_id (child session ID), with automatic completion notification. Do not sleep, poll, or duplicate delegated work; advance non-overlapping work or end your turn.

DEFAULT: Do the work yourself. Own the investigation, design decisions, coherent implementation, and final integration. The agent catalog describes capabilities, not instructions to delegate. Difficulty, file count, matching specialties, and the ability to split work are not sufficient reasons to use this tool.

Respect an explicit request to delegate or to work personally. If the user asks you to do it yourself, do not delegate any part of that task unless they later authorize it. Otherwise, decide whether delegation is justified BEFORE choosing an agent; do not reverse-engineer a task to use an available agent or ask the user to approve routine self-execution.

WHEN to delegate without an explicit request. The scope and acceptance criteria must be clear, and at least one of these must provide a concrete benefit beyond merely moving work to another model:
1. Substantial independent parallel work. Both the child assignment and your own remaining work are substantial, independently advanceable units. The child can proceed against a stable contract without waiting for your design or implementation. Keep supporting changes needed to deliver and verify the same behavior with the main implementation; different files or layers do not make them independent deliverables. Handing off the only next step and waiting is not parallelism.
2. Genuine context isolation. A bounded assignment requires processing a large body of material that you do not also need to read to make the core decisions. The result can be consumed as evidence-backed findings or code locations. A few reads or targeted searches, or material you already understand, do not justify a handoff. Do not outsource the context needed to establish the root cause or design the solution.
3. Targeted independent review or an unavailable capability. Identify the specific conclusion and failure mode needing a second perspective, or a capability you actually lack. A matching agent description, task difficulty, or generic desire for extra assurance is not a capability gap.

Even then, delegate only when the expected benefit clearly exceeds briefing, waiting, integration, and verification costs. If the choice is marginal or uncertain, continue yourself without repeatedly reconsidering delegation. Before launching, briefly state the concrete benefit and bounded assignment; for parallel work, also state the substantive work you will advance. Restating the assignment or the agent's specialty does not explain a benefit.

Investigations and root-cause work that cross-check runtime state, logs, databases, or live behavior to build a causal chain stay on the main thread. A child agent may at most take a clearly-scoped pure code-location slice of it.

AFTER deciding to delegate, choose from the configured responsibilities below. A description is not evidence that another model is more capable than you, and does not override the delegation criteria. If no available agent is a good fit, use other tools directly. Naming an agent means it does the assigned work itself; do not pass the whole assignment through to another worker.

CONCURRENCY. Only launch units simultaneously that can advance independently with no mutual waiting. Multiple agents may share read-only material, but their write scopes must not overlap; for shared interfaces or implementations, fix the contract and ownership first. Keep order-dependent steps serial. Do not re-dispatch the same scope of exploration or implementation; when there is a concrete risk you may arrange an independent review, but state the conclusion to verify and the angle.

Calls:
- Use read/glob/grep directly for specific file or symbol lookups.
- Supply description, prompt, subagent_type for one task, or tasks for up to 20 independent tasks. Async batches return batch_id, child IDs, and launch status, not work results. Give a specific title, scope, whether to edit or research, and verification criteria.
- Use wait=true only when you must block. In this mode, settled children return results/errors; children promoted to background keep running and notify later.
- task_id resumes or steers an owned child, preserving its agent, model, and permissions. Omit the agent or repeat it; invalid IDs and agent switches fail. Running corrections are admitted immediately and apply at the next safe provider-turn boundary, not after the whole task; admission does not mean applied or undo completed work.
- Children receive original user requirements and authorized ancestor evidence references. inherit_context=true additionally includes bounded recent parent history, newest messages preserved. Retrieve authorized originals with history_grep/history_list, source=task.
- Nested delegation is denied by default. allow_nested_tasks=true requires user authorization and applies only to new children; it cannot override inherited denies or change existing permissions.
- Verify child claims before relying on them. Child results are not user-visible; summarize relevant outcomes yourself.
